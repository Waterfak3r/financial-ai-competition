  ## 一、最需要处理的问题

  ### 1. 高优先级：独立核验会把某些负数误判为正数，并标为 verified

  位置：

  - backend/src/finagent/verification/independent_fact.py:27
  - backend/src/finagent/verification/independent_fact.py:227–282

  新核验器按 PyMuPDF 的独立 word 提取金额。如果负号或括号与数字分成不同 word，它会只拿中间的 100.00，忽略旁边的负号或括号。

  我用合成 PDF 复现了两种情况：

   原始页面排版         待核验事实    实际结果
  ━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━
   - 与 100.00 分开     +100.00       verified，错误通过
  ───────────────────  ────────────  ──────────────────────────
   (、100.00、) 分开    +100.00       verified，错误通过
  ───────────────────  ────────────  ──────────────────────────
   上述负数排版         -100.00       conflict，反而拒绝正确值

  这不是“不支持某种格式所以弃权”，而是错误数字被核验通过，应该优先修。

  值得注意的是，旧金额复核已经考虑了分开的负号、括号和金额边界，新独立核验没有覆盖同类反例。

  **建议：**保留独立定位逻辑，但补齐金额 token 的符号、括号、边界判断，并把这两个反例纳入正式 regression。不能以“核验模块独立”为理
  由丢掉已有的错误案例。

  ———

  ### 2. 高优先级：旧提取 → v2 → 独立核验，目前直接串不起来

  位置：

  - backend/src/finagent/schemas/financial_fact_v2.py:414–437
  - backend/src/finagent/verification/independent_fact.py:93–95、203–205

  旧事实适配器明确生成：

  unit=None

  而独立核验器要求：

  fact.unit == 原文单位

  我用真实海天年报的提取结果直接串联：

  旧提取：8 条事实
      ↓
  adapt_legacy_financial_fact
      ↓
  verify_financial_fact
      ↓
  8 条全部 conflict
  原因：单位或币种与原文相反

  这里不仅是接口没有接上，还有状态语义问题：

  > “单位尚未确认”不等于“单位与原文冲突”。

  建议：

  - 明确 v2 事实中的单位由哪个环节确认。
  - 缺失、未知和明确冲突分别处理。
  - 不要为了让流程通过，在适配器里无依据地补 "元"。
  - 用真实提取结果测试核验器，而不只使用手工填写完整字段的测试事实。

  ———

  ### 3. 高优先级：即使事实核验通过，报告模块也不能正确接收全部真实证据

  位置：

  - backend/src/finagent/verification/independent_fact.py:227–249
  - backend/src/finagent/reports/annual_report.py:484–558

  为了进一步定位问题，我仅在内存中给样例事实补上已知单位，没有改原始文件或历史 JSON。

  结果是：

  独立核验：8 / 8 verified
  报告已确认事实：4 / 8

  剩余四条被报告拒绝：

  #### 经营现金流，两条

  核验器识别行名时拼接了相邻行，但保存的 row_region 没有包含完整行名，留下的是：

  经营活动产生的现金流量净

  报告却要求证据中包含：

  经营活动产生的现金流量净额

  #### 非经常性损益，两条

  真实表题保存为：

  十、 非经常性损益项目和金额

  报告侧却要求标题严格等于：

  非经常性损益项目和金额

  另外，核验器接受 CNY 与“人民币”等价，报告侧却直接比较字符串。使用 CNY 事实时，报告会把这些本可匹配的证据拒绝。

  **这是典型的跨模块契约不一致。**不能靠不断放宽报告条件掩盖，应统一：

  - 原文标题与标准化标题；
  - 完整行标签证据的表达；
  - 币种标准值与原文值；
  - “核验通过”的最低证据要求。

  ———

  ### 4. 高优先级：追溯调整状态形成了一个尚未解决的阻塞点

  位置：

  - backend/src/finagent/schemas/financial_fact_v2.py:401–406
  - backend/src/finagent/verification/independent_fact.py:122–128
  - backend/src/finagent/finance/v2_calculation.py:117–145

  当前实际关系是：

  1. 旧提取和适配器把追溯状态保留为 unknown。
  2. 独立核验器明确表示：没有核验追溯调整状态。
  3. v2 计算器遇到 unknown，拒绝差额和同比。

  因此，前述真实样例即使八条事实核验通过，八个计算结果仍全部失败。

  这个保守限制本身符合你的路线，但目前缺少负责解除限制的证据处理环节。

  更重要的是：我仅在内存把状态改为 not_restated 后，计算就全部成功，而核验器仍声明没有核验这个字段。这说明计算器信任的是字段值，并
  不是该字段对应的验证证据。

  正确的下一步不是把 unknown 批量改成 not_restated，而是补上可比性确认的来源、检查和状态。

  ———

  ### 5. 高优先级缺口：计算与 Claim 的真正核验还没有实现

  位置：

  - backend/src/finagent/reports/annual_report.py:396–413
  - backend/src/finagent/reports/annual_report.py:467–472

  现在已经有：

  - CalculationResult
  - Claim
  - VerificationResult
  - 报告分区逻辑

  但有核验结果容器，不等于有负责产生可信结果的核验程序。

  目前报告侧：

  - 对 Claim，主要检查状态和引用对象是否进入已确认区。
  - 对计算，检查 checks 字符串是否包含“公式重算”或“结果校验”，以及公式或结果文字。

  错误注入显示：

  - 已确认事实是 100.10，Claim 写成 999999999.99，配上手工构造的 verified 记录，仍能进入“已核实主张”。
  - 给计算填入错误结果 99999，再写一句“结果校验 99999”，仍能进入“已确认计算”。

  这里不是说报告生成器必须承担所有重算和语义判断，而是：

  > 报告依赖的可信上游核验尚不存在，不能把报告分区函数当作完整核验闭环。

  建议把职责放对位置：

  - 计算核验：按受控公式和绑定的输入事实重新计算。
  - 事实、计算类 Claim：优先从结构化对象确定性生成，减少自由改写数字。
  - 推论、假设：单独验证引用支持关系，保留替代解释和限制。
  - 报告：消费这些结果，不接受自然语言“自证通过”。

  ## 六、建议的推进顺序

  ### 第一关：修复“核验不能错放”

  只围绕现有四项指标处理：

  - 分离负号、括号；
  - 单位未知与冲突；
  - 完整行标签和表题证据；
  - 币种标准化；
  - 跨公司、跨文档筛查；
  - 追溯状态的证据约束。

  验收标准：错误金额不能 verified，正常样例不能因模块格式不一致而误拦截。

  ### 第二关：打通不需要手改 JSON 的确定性 Golden Path

  保留旧预检兼容性，新增独立的年度分析入口，复用现有模块：

  PDF
  → 提取
  → v2 事实及来源
  → 独立事实核验
  → 可比性确认
  → 确定性计算及核验
  → 候选线索
  → report.json + report.md

  同时归档输入哈希、代码版本、规则版本、证据和失败原因。

  验收标准：一个正式命令能完成，不靠测试辅助函数、不手工补字段、不隐藏失败。

  ### 第三关：接入最小解释与调查流程

  再引入简化的 LangGraph：

  - 只调查已出现的候选线索；
  - 检索本次年报中的 MD&A / 附注；
  - 模型输出有来源的解释和替代解释；
  - 限制补检次数；
  - 接入现有调用审计；
