# 开发协作与交接

协作分工的唯一规则入口是 [AGENTS.md](../AGENTS.md)。OMP 的项目配置和可执行角色定义位于 [.omp/](../.omp/)，本文维护交接、配置与整合步骤，不另设一套分工或固定型号规则。

## 任务交接

每次交接写明主控确定的路线与方案、本次目标、关键步骤、文件归属、需要保留的现有改动、相关契约、验收标准和实际验证方式。执行端须知道工作区还有其他协作者，不撤销他人改动。验收不通过时在原任务修正；关联任务复用与新任务启动按 AGENTS 的上下文规则处理。

开始前检查现有模块与 Git 状态；报告“已编码、已集成、已验证”的具体范围，区分构造测试、真实资料、本地 mock、在线调用和历史回放。不得把工具或依赖在旧环境可用写成当前环境已就绪。

## OMP 配置与入口

从仓库根目录运行 `omp`。OMP 18.8.9 的项目设置读取进程当前目录下的 [.omp/config.yml](../.omp/config.yml)，从子目录启动不会自动向上查找该设置文件；角色发现规则则见 [OMP 任务代理文档](https://github.com/can1357/oh-my-pi/blob/v18.8.9/docs/task-agent-discovery.md)。

项目配置的 `modelRoles` 维护角色别名，角色文件通过别名选择模型；职责与模型选择分开。主控使用 `default`，子代理职责如下：

| 代理 | 模型角色 | 交付责任 |
| --- | --- | --- |
| `implementer` | `implement` | 完成一个文件归属明确的实现切片，交付增量补丁与验证证据 |
| `writer` | `draft` | 按主控提纲和可信材料完成结构、逻辑与事实完整的初稿 |
| `editor` | `polish` | 基于完整初稿润色语言，不新增实质内容 |
| `reviewer` | `review` | 独立只读审查代码或文字的合同、差异和证据 |
| `scout` | `scout` | 按需定位代码、契约与已有能力，不修改文件 |

项目角色可以使用 `@default`，但这不保证它们最终使用同一模型，也不证明已建立跨模型协作。可在 `/model` 的 Roles 视图分配角色，或直接修改项目配置，值使用 OMP 可识别的 `provider/model`，按需要附加推理级别。`modelRoleStorage: project` 让角色分配写入项目配置；`default` 未在项目配置设置时沿用全局配置。具体型号和推理级别只在配置中维护，不在任务书绑定执行模型。

使用 `omp config list --json` 查看有效设置；该命令只读。`omp config set`、普通 `/settings` 和 `/agents` 的覆盖设置通常写入全局配置，不用于维护这份项目设置。`task.agentModelOverrides[代理名]` 优先于角色文件的模型别名，已有全局覆盖会被继承；角色分配后仍应检查它是否绕过了目标映射。CLI、临时覆盖、环境配置和扩展也可能改变实际选择，应核对解析后的模型标识，不能只看角色名。模型凭据继续由本机 OMP 管理，不写入项目文件；开发模型配置与应用的 `.env.model` 无关。配置格式和优先级见 [OMP 设置文档](https://github.com/can1357/oh-my-pi/blob/v18.8.9/docs/settings.md)。

项目关闭 OMP 模型自动回退，清空 `retry.fallbackChains`，禁用 `retry.usageAwareFallback`，启用 `retry.waitForUsageReset`：供应方报告额度耗尽且提供重置时间时等待重置，不自动切换其他模型。精确设置只在 [.omp/config.yml](../.omp/config.yml) 维护；主模型角色绑定不因此改变。开工核对有效配置，派发后核对宿主实际模型标识；职责隔离不等于跨模型独立验证。这些设置只影响 OMP 开发协作，不影响应用 `.env.model`、供应方配置或历史运行。型号不可用时保留失败事实，不在配置之外擅自切换模型；账号和凭据不写入交接材料。项目禁用内置安全审查代理，但不放宽资料与凭据保护要求。

## 派发与补丁整合

原生 `task` 的批量输入用 `context` 共享目标和接口合同，各项 `task` 写明目标文件、改动要求及验收结果，`solutionSpace` 描述仍待解决的设计或原因。明确设置 `agent`：实现、初稿、润色分别使用 `implementer`、`writer`、`editor`，默认设置 `isolated: true`；调查使用 `scout`，审查使用 `reviewer`，两者设置 `isolated: false`。不以无角色的通用任务替代项目角色；存在前后依赖的任务顺序派发。

共享 `context` 用 `# Goal` 与 `# Contract` 固定目标、接口、数据保护和现有改动；每项 `task` 用 `# Target`、`# Change`、`# Acceptance` 写文件所有权、非目标、改动与可观察的结果，避免重复大段背景。`solutionSpace` 说明未确定的设计或原因，不描述工作量。真正独立的切片一次批量派发；共享文件只有一个负责人，接口变化通过 `write agent://<id>` 同步。调查、实现、审查各阶段使用最具体的角色，代理不再转派。

隔离模式复制任务起点的 checkout，OMP 记录起点基线并输出本任务增量；它不要求先提交用户的未提交改动。自动回填关闭后，主控读取任务结果中的 `patchPath` 并检查完整补丁。独立审查需同时提供任务合同、起点信息、补丁位置和专项验证证据；审查者没有 shell 或写入工具，重跑验证由主控或实现者执行。

若隔离复制起点失败，先记录工具错误及是否已有增量；不要通过暂存、提交、恢复或移走用户文件让隔离“成功”。按 AGENTS 的降级条件，可显式 `isolated: false` 在主工作区执行：派发前保存任务文件起点，唯一指定共享文件负责人，要求只改所有权范围，并把任务增量交给独立 reviewer。主工作区改动不再执行 `git apply`；其他隔离补丁仍按下述顺序检查和回收。失败副本不作为已完成产物。

主控在仓库根目录对明确的补丁路径先运行 `git apply --check <patchPath>`，核对内容及该阶段应有的审查结果后再执行 `git apply <patchPath>`；实现补丁先经独立审查，文字任务的中间交接见下节。每次只回收一个补丁，再检查差异及验收结果。检查失败时对齐当前工作区并修正补丁，不强制应用。共享文件或依赖接口发生变化时，后续任务从最新整合状态派发；复用旧隔离代理须先同步相关变化。最终整合检查按变更风险选择，不重复运行无关的全量检查。

项目 [.gitattributes](../.gitattributes) 将 Word（`.docx`）按二进制处理，防止系统级 `diff=astextplain` 等 textconv 把隔离起点的修改或删除转换为只能阅读、不能应用的文本差异。手工生成可回收补丁时使用 `git diff --no-textconv --binary`，不把转换后的文本差异交给 `git apply`。文件已废弃时保留其删除，不通过恢复原件绕过隔离失败；配置修正后的隔离启动与补丁回收仍须实际验收。

任务结果保留补丁、验证证据与未完成事项，按照项目文件归属保存需要长期复现的证据。OMP 自身的隔离副本按工具生命周期管理，不能依赖副本永久存在；主工作区、项目 tmp/ 和用户原始资料不得随任务结束自动清理。Agent Hub（`Alt+A`）可查看代理活动并追加消息；主控也可使用 `write agent://<id>` 继续同一任务，能力以当前宿主为准。

修改期间先完成切片，不逐次编辑后反复跑构建、检查或格式化。补丁稳定后由主控安排一次受影响验证；有失败时先修复具体原因，再运行相关检查。UI 改动必须在实际浏览器表面验证，CLI/API 改动必须执行相应路径；单元测试、typecheck/build 或 reviewer 的静态审查不能替代运行证明。验证记录保留命令、退出码、原始输出和场景边界，来源与真实在线授权仍按数据规则核对。

## 路线与文字审查

代码任务给 reviewer 的输入包括主控方案、可观察的验收项、实际改动与验证证据。要求其说明哪些验收项得到支持、哪些存在问题或尚未验证；实现者退出成功、局部代码完成或测试通过不能单独证明路线要求全部达到。

文字任务的主控交接同时明确读者、用途、提纲、可信事实来源及必须保留的结论和限定。writer 完成初稿后，主控检查范围并保存可对照的完整初稿；确认补丁后顺序回收，editor 从包含该初稿的最新工作区启动，不能只收到旧稿或补丁摘要。语言润色不新增实质内容，表达调整只要保持含义与路线即可。

`tmp/` 中被 Git 忽略的初稿不保证随隔离起点复制。此类临时稿由主控提供完整、版本明确的只读快照，例如 `local://` 文件；editor 必须先读取全文，再写入自己的指定产物，不能只收到概要，也不能依赖另一代理的隔离目录长期存在。临时文件若需进入宿主增量，只能在该代理的隔离副本中精确加入本任务文件，不批量暂存、更不能在主工作区暂存用户文件。正式文稿仍从主控已经回收的最新版本交接。

editor 完成后，将主控要求、可信材料、链路中的既有版本（如有）、完整初稿、润色终稿及版本对应的差异一并交给独立 reviewer。主审对象是 editor 的最终稿：先检查最终稿的表达、逻辑和可信依据，再对照前版核对原意、论证关系、核心结论、重要限定与完成状态是否偏移；合理措辞变化不要求逐字还原。新增或沿用的事实、数据、引用、来源、能力、验收结果和承诺都检查是否编造或缺少依据，初稿已有问题不能因终稿照抄而放行。主控可提供明确可读的任务产物，或为审查回收润色补丁；回收不代表已验收。二进制文稿须提供对应版本的可读全文，排版验收另附版式证据。内容或逻辑问题交回 writer，纯表达问题交回 editor，修正后复核相关变化，再由主控最终验收。初稿对照副本进入所属 `tmp/<task_id>/`，长期交付及验收证据按项目归属保存。

## 范围与兼容

当前首版不做 OCR、向量库、GraphRAG、模型训练、用户系统和云部署。用户明确安排的新范围按任务更新路线，不能用历史“暂不做”否定后续授权。

保留旧预检 API 和历史记录的兼容；已有原始资料与归档不改写。修复旧实现不等于改写历史结果，必要的 API 行为修正应说明兼容影响并验证。

计划书可按用户任务完善；视频脚本与制作交接给视频负责人，软件侧交付可录系统与证据。上传由团队指定提交负责人。材料编写、视频制作和软件实现分别验收。
